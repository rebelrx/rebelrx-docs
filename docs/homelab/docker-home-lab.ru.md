# 🐳 Homelab на Docker (Devuan + Compose)

Практическое руководство по развёртыванию **чистого, воспроизводимого homelab на Docker** на «голом железе» с использованием Devuan и Docker Compose.

Большинство руководств по homelab предполагают Debian, Ubuntu или другой дистрибутив с systemd. Это руководство идёт другим путём: **Devuan** — Debian *без* systemd — ради более лёгкой базы с простой системой инициализации, которую вы полностью контролируете. Стеки Compose взяты из [homelab-репозитория RebelRx](https://github.com/rebelrx/rebelrx-homelab) и одинаково работают на любом Docker-хосте; здесь мы настраиваем их «по-девуановски».

---

## 🔥 Почему Docker (а не Proxmox)

Использовать Proxmox *можно*. Многие так и делают.

Но для большинства homelab он привносит лишнюю сложность.

### ❌ Недостатки Proxmox

- Накладные расходы виртуальных машин (потери CPU и RAM)
- Больше слоёв для отладки
- Усложнение резервного копирования
- Сеть становится сложнее, чем должна быть
- Провоцирует фрагментацию (множество мелких VM вместо единой системы)

---

### ✅ Почему Docker на «голом железе» предпочтительнее

- **Лёгкий** → без накладных расходов виртуализации  
- **Простой** → одна ОС, одна система для администрирования  
- **Быстрое развёртывание** → сервисы поднимаются за секунды  
- **Воспроизводимый** → всё описано в Compose  
- **Переносимый** → весь стек переезжает вместе с Git  

> 💡 Если вы не запускаете корпоративные мультиарендные нагрузки, гипервизор вам, скорее всего, не нужен.

## 🔑 Добавление репозитория Docker

`.deb`-репозиторий Docker привязан к кодовым именам **Debian**, а у Devuan свои
кодовые имена (`daedalus`, `excalibur`, …), которые репозиторий Docker не распознаёт.
Сопоставьте их с той базой Debian, на которой построен ваш выпуск Devuan.

```bash
sudo install -m 0755 -d /etc/apt/keyrings

curl -fsSL https://download.docker.com/linux/debian/gpg | \
  sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg

# У Devuan свои кодовые имена; Debian-репозиторию Docker нужна база Debian:
#   Devuan 5  "Daedalus"  → bookworm
#   Devuan 6  "Excalibur" → trixie
DEBIAN_CODENAME=trixie   # укажите базу Debian, соответствующую вашему выпуску Devuan

echo \
  "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] \
  https://download.docker.com/linux/debian \
  $DEBIAN_CODENAME stable" | \
  sudo tee /etc/apt/sources.list.d/docker.list > /dev/null
```

## 📁 Структура каталогов

Держите **конфигурацию и данные в раздельных деревьях** — это самое важное решение
по компоновке, и каждый стек в репозитории ему следует:

```bash
/opt/stacks/<stack>/     # Стеки Docker Compose (compose.yaml, .env, README)
/opt/data/<stack>/       # Постоянные данные приложений (никогда не коммитятся в Git)
```

Пример:

```bash
/opt/stacks/
├── npm/
│   ├── compose.yaml
│   ├── .env
│   └── README.md
├── plex/
└── ...

/opt/data/
├── npm/
├── plex/
└── ...
```

### Почему это важно

- Разделение **конфигурации и данных**
- Проще резервное копирование (снимок `/opt/data`; дерево compose живёт в Git)
- Чище Git-репозитории (данные времени выполнения никогда не версионируются)
- Предотвращает «расползание» Docker

> 💡 `/opt/stacks` — это ещё и путь по умолчанию `DOCKGE_STACKS_DIR` в Dockge,
> поэтому менеджер стеков подхватывает всё без дополнительной настройки.

## 🧠 Ключевые концепции (сначала прочтите это)

### 1. Мышление «Compose прежде всего»

Всё описывается в YAML.

- Никаких кликов по графическим интерфейсам
- Никакого ручного создания контейнеров
- Git = источник истины

---

### 2. Файлы `.env`

Каждый стек использует переменные окружения:

```env
PUID=1000
PGID=1000
TZ=America/New_York
```

**Почему это важно:**

- Единообразные права доступа
- Переносимые конфигурации
- Лёгкое переопределение значений

Секреты (пароли, API-ключи) тоже живут в `.env`, который **исключён из Git**.
В репозиторий попадают только шаблоны `.env.example` с пустыми секретами.

---

### 3. Монтирование томов

```yaml
volumes:
  - /opt/data/plex:/config
```

Это гарантирует:

- Данные сохраняются между перезапусками контейнера
- Простое резервное копирование (всё лежит в `/opt/data`)
- Полный контроль над хранилищем

---

### 4. Привязка портов

```yaml
ports:
  - 8080:8080              # опубликован на всех интерфейсах — доступен в вашей LAN
  # - 127.0.0.1:8080:8080  # только loopback — доступ через обратный прокси
```

**Как это устроено в репозитории:**

- Веб-интерфейсы по умолчанию публикуются на **всех интерфейсах**, чтобы сразу
  работать в вашей локальной сети.
- Добавьте префикс `127.0.0.1:` к привязке, чтобы оставить сервис **только на loopback**
  и обращаться к нему исключительно через обратный прокси.
- **Внутренние сервисы** (базы данных, Redis/Valkey, брокеры) **вообще не публикуют
  порты хоста** — они доступны только во внутренней сети стека.

## 🌐 Обратный прокси (Nginx Proxy Manager)

Рекомендуемый подход — стек `npm` из репозитория:

- Запустите **Nginx Proxy Manager (NPM)**
- Публикуйте сервисы через поддомены
- SSL настраивается автоматически

Сервисы подключаются к общей сети `proxy_net`; NPM обращается к каждому по имени
контейнера, поэтому обратный прокси работает независимо от того, опубликован ли
порт на хосте.

Пример:

```text
https://plex.вашдомен.com
```

Преимущества:

- Никакой возни с портами
- Чистые URL-адреса
- Централизованный контроль доступа

## ▶️ Запуск первого стека

Начните с обратного прокси, чтобы всему остальному было за чем «спрятаться»:


Затем:


## ⚠️ Типичные ошибки

### ❌ Проблемы с правами доступа

Файлы Compose могут принадлежать вашему пользователю; каталоги **данных** обычно
принадлежат `PUID:PGID` контейнера (часто `1000:1000`):

```bash
sudo chown -R $USER:$USER /opt/stacks/<stack>
sudo chown -R 1000:1000 /opt/data/<stack>   # укажите PUID/PGID соответствующего стека
```

---

### ❌ Порты уже заняты

```bash
ss -tulnp | grep :ПОРТ
```

---

### ❌ Контейнеры не обновляются

```bash
docker compose pull
```

---

### ❌ Правка работающих контейнеров

Не делайте этого.

Отредактируйте **файл Compose** и разверните заново.
