# 🗂️ Монтирование NAS-хранилища (Devuan)

NAS хранит основной массив данных; сервер запускает сервисы. Это руководство соединяет их **надёжно**: монтирования, которые переживают перезагрузки, корректно ведут себя под sysvinit и не подсовывают молча пустые каталоги вашим Docker-контейнерам.

---

## ⚠️ Основной принцип

> Хранилище должно быть скучным. Монтирование, о котором приходится думать, — это монтирование, которое вас подведёт.

---

## 🧭 NFS или SMB?

Работают оба. Выбирайте исходя из того, кто с кем общается:

| | NFS | SMB / CIFS |
| :--- | :--- | :--- |
| Лучше всего для | Linux ↔ Linux / NAS | Смешанные сети (Windows, принтеры, сканеры) |
| Производительность | Быстрее, меньше накладных расходов | Немного тяжелее |
| Права доступа | Unix UID/GID, нативно | Сопоставляются при монтировании |
| Модель аутентификации | По хосту/IP (v3/v4) | Имя пользователя + пароль |
| Вердикт | **Выбор по умолчанию для Linux-homelab** | Когда NFS недоступен или данные раздаёт Windows |

Руководство охватывает оба варианта — NFS как основной путь.

---

## 🖥️ Подготовка на стороне NAS

На NAS (QNAP, Synology, TrueNAS — интерфейсы разные, концепции одни):

1. Создайте или выберите общую папку (например, `media`, `backups`)
2. Включите **службу NFS** и добавьте NFS-правило для общего ресурса:
    - Разрешённый клиент → IP вашего сервера (или его Tailscale-IP, если монтируете через tailnet)
    - Доступ → чтение/запись
    - Squash → *no root squash* только если Docker-контейнеры должны писать от root; иначе сопоставляйте с конкретным UID/GID
3. Для SMB → создайте выделенного низкопривилегированного пользователя NAS для сервера; никогда не монтируйте под учётной записью администратора NAS

!!! tip "Один общий ресурс на одно назначение"

    Отдельные ресурсы для `media`, `backups` и `archive` означают отдельные
    права, отдельные NFS-правила и возможность размонтировать один, не трогая
    остальные. Не поддавайтесь искушению завести один гигантский
    «ресурс-для-всего».


## 🧪 Сначала пробное монтирование (всегда)

Никогда не идите сразу в `fstab`. Сначала докажите, что монтирование работает, в интерактивном режиме:

```bash
# Посмотреть, что экспортирует NAS
showmount -e 192.168.1.xx

# Создать точку монтирования и проверить
sudo mkdir -p /mnt/nas/media
sudo mount -t nfs -o vers=4.1 192.168.1.xx:/media /mnt/nas/media

# Проверка: вывести содержимое, записать, прочитать обратно
ls /mnt/nas/media
touch /mnt/nas/media/.write-test && rm /mnt/nas/media/.write-test
```

Если проверка записи не проходит, исправьте права **сейчас** (см. «Устранение неполадок») — сломанное монтирование в `fstab` куда менее приятно отлаживать во время загрузки.

Размонтируйте, прежде чем делать постоянным:

```bash
sudo umount /mnt/nas/media
```

## 📌 Постоянные монтирования через /etc/fstab

### NFS

```bash
sudo nano /etc/fstab
```

Добавьте по одной строке на каждый общий ресурс:

```text
192.168.1.xx:/media    /mnt/nas/media    nfs    rw,hard,vers=4.1,_netdev,nofail    0    0
192.168.1.xx:/backups  /mnt/nas/backups  nfs    rw,hard,vers=4.1,_netdev,nofail    0    0
```

Что даёт каждая опция:

- `hard` → если NAS пропадает, ввод-вывод **ждёт** его возвращения вместо того, чтобы молча возвращать ошибки и портить записи. Правильно для данных, которые вам дороги.
- `vers=4.1` → фиксирует версию протокола; никаких сюрпризов согласования после обновлений прошивки NAS
- `_netdev` → сообщает init-скриптам, что этому монтированию сначала нужна сеть — **критично на sysvinit**
- `nofail` → выключенный NAS не подвесит загрузку всего сервера

Примените и проверьте:

```bash
sudo mount -a
df -h | grep nas
```

### SMB

Учётные данные никогда не пишутся в `fstab` (он доступен на чтение всем). Используйте файл с учётными данными:

```bash
sudo nano /root/.smb-credentials
```

```text
username=serversvc
password=ваш-надёжный-пароль
```

```bash
sudo chmod 600 /root/.smb-credentials
```

Затем в `/etc/fstab`:

```text
//192.168.1.xx/media  /mnt/nas/media  cifs  credentials=/root/.smb-credentials,uid=1000,gid=1000,vers=3.0,_netdev,nofail  0  0
```

`uid=1000,gid=1000` присваивает каждый файл вашему пользователю — задайте его так, чтобы он совпадал с `PUID`/`PGID`, под которыми работают ваши [Docker-стеки](docker-home-lab.md).

## 🔁 Поведение при загрузке без systemd

На Devuan последовательность загрузки sysvinit обрабатывает это корректно **благодаря `_netdev`**: стадия `mountnfs` выполняется после поднятия сети и монтирует всё, что в fstab помечено как зависящее от сети. Никаких юнитов, никаких конфигураций автомонтирования — механизм тридцатилетней давности просто работает.

Проверьте после следующей перезагрузки:

```bash
df -h | grep nas
```

!!! tip "Монтирование по требованию с autofs (опционально)"

    Если NAS иногда выключен, `autofs` монтирует общие ресурсы только при
    обращении к ним и освобождает их после простоя — вообще никакой зависимости
    при загрузке:

    ```
    sudo apt install -y autofs
    ```

    Затем опишите свои ресурсы в `/etc/auto.master.d/`. Для постоянно включённого
    NAS обычный fstab проще и лучше; беритесь за autofs, только когда NAS
    действительно работает с перебоями.

## 🐳 Подводный камень Docker

Вот режим отказа, который однажды кусает каждого:

**Если Docker стартует раньше, чем смонтируется NAS, контейнеры получают bind-mount пустого каталога** — и некоторые приложения радостно инициализируют в нём свежую пустую библиотеку. Jellyfin, просканировав пустую папку с медиа, удаляет свои метаданные; задача резервного копирования, увидев пустой источник, «успешно» копирует ничего.

Средства защиты, в порядке ценности:

**1. Дайте порядку загрузки сделать своё дело.** На sysvinit `mountnfs` выполняется до init-скрипта Docker — при заданном `_netdev` *доступный* NAS монтируется до запуска контейнеров. Риск в том, что NAS может быть медленным или выключенным (что `nofail` сознательно допускает).

**2. Защитите стеки, зависящие от монтирования.** Добавьте проверку в последовательность init Docker — создайте `/etc/init.d/wait-for-nas`:

```bash
#!/bin/sh
### BEGIN INIT INFO
# Provides:          wait-for-nas
# Required-Start:    $network $remote_fs
# Required-Stop:
# Default-Start:     2 3 4 5
# Default-Stop:
# X-Start-Before:    docker
# Short-Description: Delay boot until NAS shares are mounted
### END INIT INFO

case "$1" in
  start)
    for i in $(seq 1 30); do
      mountpoint -q /mnt/nas/media && exit 0
      sleep 2
    done
    echo "wait-for-nas: NAS not mounted after 60s, continuing anyway"
    ;;
  *) ;;
esac
exit 0
```

```bash
sudo chmod +x /etc/init.d/wait-for-nas
sudo update-rc.d wait-for-nas defaults
```

**3. Сделайте пустоту обнаружимой.** Разместите файл-маркер на ресурсе NAS (`touch /mnt/nas/media/.nas-mounted`, пока он смонтирован). Любой скрипт — особенно резервного копирования — сможет отказаться работать с несмонтированным путём:

```bash
[ -f /mnt/nas/media/.nas-mounted ] || { echo "NAS не смонтирован, прерывание"; exit 1; }
```

> Трюк с файлом-маркером не стоит ничего, а спас больше данных homelab, чем любые другие три строки этого руководства.

## 🚫 Чего не делать

!!! danger "Никогда не запускайте базы SQLite поверх NFS или SMB"

    Стек Arr (Sonarr, Radarr, Prowlarr…), Jellyfin и многие homelab-приложения
    используют **SQLite**, который полагается на файловые блокировки, а сетевые
    файловые системы реализуют их ненадёжно. Базы данных на NAS-монтированиях
    повреждаются — вопрос не «*если*», а «*когда*».

    Правило из [руководства по Docker](docker-home-lab.md) уже решает это:

    - Данные приложений и базы данных → `/opt/data/<stack>` на **локальном диске**
    - Массивы медиа, документы, резервные копии → монтирование NAS

- Не монтируйте под учётной записью администратора NAS — выделенный низкопривилегированный пользователь, на каждый ресурс
- Не используйте `soft`-монтирования для всего, что пишет — тихие частичные записи и есть тот способ, которым портятся файлы. ([Руководство по серверу Devuan](../linux/devuan-server-install.md) сознательно использует `soft` для преимущественно читаемых ресурсов, чтобы headless-машина оставалась отзывчивой — это другая сторона того же компромисса)
- Не храните учётные данные в `fstab` — файл с учётными данными, `chmod 600`
- Не пропускайте интерактивное пробное монтирование — fstab существует, чтобы *записать* работающее монтирование, а не чтобы *обнаружить* сломанное

## 🧰 Устранение неполадок

- **`access denied by server`** → NFS-правило на NAS не включает IP вашего сервера, либо неверен путь экспорта. Перепроверьте через `showmount -e <ip-nas>`.
- **Файлы принадлежат `nobody:nogroup`** → несоответствие маппинга ID в NFSv4. Самое простое решение в домашней сети: сделайте UID/GID на ресурсе NAS совпадающими с вашим пользователем сервера (1000:1000) или настройте squash-опцию ресурса на сопоставление всех обращений с этим UID.
- **`Stale file handle`** → экспорт изменился на стороне NAS, пока был смонтирован. `sudo umount -l /mnt/nas/media && sudo mount -a`.
- **Команды бесконечно висят на точке монтирования** → NAS недоступен, а монтирование `hard` (работает как задумано — сохранность данных важнее отзывчивости). Верните NAS в строй или принудительно освободите: `sudo umount -f -l`.
- **Медленные передачи по SMB** → убедитесь, что в опциях монтирования стоит `vers=3.0` или выше; согласование SMB1 всё ещё прячется в старых настройках NAS по умолчанию и одновременно медленное и небезопасное.

## 🧠 Финальная мысль

NAS, до которого нельзя надёжно достучаться, — это просто очень дорогой обогреватель.

Сделайте монтирования скучными — проверенными, зафиксированными, упорядоченными, защищёнными — и остальной homelab сможет строиться на хранилище, о котором никогда не приходится думать.

> Скучное хранилище — это фундамент, на котором стоит всё остальное.
