# 💾 Резервное копирование и восстановление (Docker-homelab)

Практическое руководство по построению **многоуровневой, проверенной системы резервного копирования** для [Docker-homelab](docker-home-lab.md) — и по доказательству её работоспособности до того, как она понадобится.

---

## ⚠️ Основной принцип

> Если ваша стратегия резервного копирования не проверена — её не существует.

Резервные копии — не продукт, который устанавливают. Это **дисциплина**: копии в правильных местах, автоматизированные без вашего участия и восстанавливаемые по расписанию, чтобы доказать свою реальность.

---

## 🧭 Правило 3-2-1

Базовый уровень, которому должна соответствовать любая стратегия:

- **3** копии данных (оригинал + две резервные)
- **2** разных носителя или системы хранения
- **1** копия за пределами дома

Для этого homelab всё раскладывается чисто:

| Копия | Где | Инструмент |
| :--- | :--- | :--- |
| 1 (рабочая) | Сервер → `/opt/data` | — |
| 2 (локальная) | NAS | Kopia |
| 3 (внешняя) | Зашифрованный удалённый репозиторий | Borg (borgmatic) |

> Локальные копии защищают от ошибок и умерших дисков. Внешняя — от пожара, кражи и вымогателей.

---

## 📦 Что бэкапить (и что не надо)

Не все данные заслуживают одинакового обращения. Разделите на уровни:

### 🔴 Невосполнимое (бэкапить на всех уровнях)

- Данные приложений → `/opt/data/<stack>` (библиотека Immich, документы Paperless, файлы Nextcloud, хранилище Vaultwarden)
- Дампы баз данных (см. ниже)
- Фотографии, документы, личные архивы

### 🟡 Восстановимое с усилиями (бэкапить локально)

- Конфигурация сервисов, ещё не зафиксированная в Git
- Библиотеки метаданных, на кураторство которых ушли годы

### 🟢 Повторно добываемое (не бэкапить)

- Медиабиблиотеки, управляемые стеком Arr
- Образы контейнеров (до них — один `docker compose pull`)
- Кэши, транскоды, миниатюры

!!! tip "Ваше дерево compose уже забэкаплено"

    Согласно [структуре homelab](docker-home-lab.md), всё в `/opt/stacks/`
    живёт в Git (Forgejo). Это и есть резервная копия вашей инфраструктуры —
    именно поэтому секреты остаются в файлах `.env` и не попадают в репозиторий.

    Это руководство покрывает вторую половину: `/opt/data/`.

## 🗄️ Базы данных: тихий убийца бэкапов

Копирование файлов **работающей** базы данных производит повреждённый бэкап достаточно часто, чтобы испортить то единственное восстановление, которое имеет значение. Postgres, MySQL и MariaDB пишут непрерывно; файловый снимок посреди записи — подбрасывание монетки.

Решение простое: **сначала дамп, потом бэкап дампов.**

Создайте `/opt/scripts/db-dumps.sh`:

```bash
#!/bin/sh
# Ночные дампы баз данных — безопасные на уровне файлов копии, которые подберут задания резервного копирования
set -eu

DUMP_ROOT=/opt/data/db-dumps
mkdir -p "$DUMP_ROOT"

# Контейнеры Postgres: docker exec + pg_dumpall
for c in immich-postgres paperless-db joplin-db forgejo-db; do
  docker exec "$c" sh -c 'pg_dumpall -U "$POSTGRES_USER"' | \
    gzip > "$DUMP_ROOT/${c}.sql.gz.tmp" && \
    mv "$DUMP_ROOT/${c}.sql.gz.tmp" "$DUMP_ROOT/${c}.sql.gz"
done

# Контейнеры MariaDB
for c in seafile-mysql romm-db; do
  docker exec "$c" sh -c 'mariadb-dump -uroot -p"$MYSQL_ROOT_PASSWORD" --all-databases' | \
    gzip > "$DUMP_ROOT/${c}.sql.gz.tmp" && \
    mv "$DUMP_ROOT/${c}.sql.gz.tmp" "$DUMP_ROOT/${c}.sql.gz"
done
```

Подгоните списки контейнеров под свои стеки и запланируйте выполнение каждую ночь **до** запуска заданий резервного копирования:

```bash
sudo chmod +x /opt/scripts/db-dumps.sh
sudo crontab -e
```

```text
# Дампы в 01:00, локальный бэкап в 02:00, внешний в 03:00
0 1 * * * /opt/scripts/db-dumps.sh
```

> Паттерн `.tmp` + `mv` гарантирует, что бэкап никогда не подхватит недописанный дамп.

## 🟢 Уровень 2 — Локальные бэкапы с Kopia (сервер → NAS)

[Kopia](https://kopia.io/) даёт быстрые, дедуплицированные, зашифрованные снимки с аккуратным веб-интерфейсом — идеально для высокочастотного локального уровня.

**Предварительное условие:** NAS смонтирован на сервере (например, в `/mnt/nas/backups` по NFS).

### Compose-стек

`/opt/stacks/backup/compose.yaml`:

```yaml
services:
  kopia:
    image: kopia/kopia:latest
    container_name: kopia
    restart: unless-stopped
    hostname: server-backup
    environment:
      - KOPIA_PASSWORD=${KOPIA_REPO_PASSWORD}
      - TZ=${TZ}
    command:
      - server
      - start
      - --insecure                  # доступ к UI только через Tailscale; TLS опционален
      - --address=0.0.0.0:51515
      - --server-username=${KOPIA_UI_USER}
      - --server-password=${KOPIA_UI_PASSWORD}
    ports:
      - "51515:51515"
    volumes:
      - /opt/data/kopia/config:/app/config
      - /opt/data/kopia/cache:/app/cache
      - /opt/data/kopia/logs:/app/logs
      - /opt/data:/source/opt-data:ro        # то, что бэкапим (только чтение)
      - /mnt/nas/backups/kopia:/repository   # куда складываем
```

!!! warning "Монтируйте источники только на чтение"

    `:ro` на монтировании источника означает, что скомпрометированный или
    сбоящий контейнер резервного копирования **не может изменить данные, которые
    защищает**. Инструментам бэкапа нужен доступ на чтение — и никогда на запись —
    к вашим рабочим данным.

### Инициализация и расписание

Откройте `http://server:51515` (через Tailscale), создайте репозиторий в `/repository` и определите политику снимков для `/source/opt-data`:

- **Расписание** → ежедневно в 02:00
- **Хранение** → 7 ежедневных, 4 еженедельных, 6 ежемесячных
- **Исключения** → каталоги кэша, папки транскодов, всё из 🟢-уровня

Пароль репозитория (`KOPIA_REPO_PASSWORD`) шифрует всё в состоянии покоя.

!!! danger "Храните пароль репозитория вне системы, которую он защищает"

    Бэкап, зашифрованный паролем, существующим только на мёртвом сервере, —
    не бэкап. Держите пароли и ключи репозиториев в менеджере паролей **и**
    в одной офлайн-копии (распечатанной, в надёжном месте).

## 🔴 Уровень 3 — Внешний бэкап с Borg (borgmatic)

[Borg](https://www.borgbackup.org/) обеспечивает зашифрованные, дедуплицированные архивы с поддержкой режима только-добавления; [borgmatic](https://torsion.org/borgmatic/) оборачивает его в один декларативный конфигурационный файл.

Для удалённой стороны выберите Borg-совместимый хостинг — устоявшиеся варианты это [BorgBase](https://www.borgbase.com/) и [rsync.net](https://rsync.net/), либо другая машина под вашим контролем (дом родственника, вторая площадка) — работает так же хорошо и оставляет всё «в семье».

> Всё шифруется **на стороне клиента** до того, как покинуть ваш сервер. Удалённый хост хранит шифротекст, который не может прочитать.

### Compose-стек

Добавьте в тот же стек `backup`:

```yaml
  borgmatic:
    image: ghcr.io/borgmatic-collective/borgmatic:latest
    container_name: borgmatic
    restart: unless-stopped
    environment:
      - BORG_PASSPHRASE=${BORG_PASSPHRASE}
      - TZ=${TZ}
    volumes:
      - /opt/data:/mnt/source:ro                          # источник (только чтение)
      - /opt/data/borgmatic/config:/etc/borgmatic.d       # конфиг + crontab
      - /opt/data/borgmatic/borg-config:/root/.config/borg
      - /opt/data/borgmatic/cache:/root/.cache/borg
      - /opt/data/borgmatic/ssh:/root/.ssh                # ключ для удалённого репозитория
```

### Конфигурация

`/opt/data/borgmatic/config/config.yaml`:

```yaml
source_directories:
  - /mnt/source

exclude_patterns:
  - '*/cache/*'
  - '*/transcodes/*'
  - /mnt/source/kopia          # не бэкапим кэш локального инструмента резервного копирования

repositories:
  - path: ssh://xxxxxxxx@xxxxxxxx.repo.borgbase.com/./repo
    label: offsite

keep_daily: 7
keep_weekly: 4
keep_monthly: 12

checks:
  - name: repository
    frequency: 2 weeks
  - name: archives
    frequency: 1 month
```

`/opt/data/borgmatic/config/crontab.txt`:

```text
0 3 * * * PATH=$PATH:/usr/local/bin borgmatic --verbosity -1 --syslog-verbosity 1
```

Инициализируйте репозиторий один раз:

```bash
docker exec borgmatic borgmatic repo-create --encryption repokey-blake2
docker exec borgmatic borgmatic key export --paper   # распечатайте это. серьёзно.
```

!!! tip "Зачем и Kopia, и Borg?"

    Два независимых инструмента означают, что одно неудачное обновление, баг или
    повреждение репозитория не смогут уничтожить все копии ваших данных разом.
    Локальный уровень оптимизирован под быстрые частые восстановления; внешний —
    под выживание в катастрофе.

    Хотите только один? Borg + borgmatic на NAS **и** во внешний репозиторий
    закрывает 3-2-1 одной цепочкой инструментов.

## 🔁 Тестирование восстановления (та часть, которую все пропускают)

Непроверенный бэкап — это надежда, а не план. Внесите в календарь **ежеквартальные учения по восстановлению**. Тридцать минут, четыре проверки:

### 1. Восстановить файл (Kopia)

Выберите настоящий файл, восстановите его в другое место, сверьте содержимое:

```bash
docker exec kopia kopia snapshot list /source/opt-data
docker exec kopia kopia restore <snapshot-id>/immich/library/some-photo.jpg /tmp/restore-test/
```

### 2. Восстановить файл (Borg)

```bash
docker exec borgmatic borgmatic list
docker exec borgmatic borgmatic extract --archive latest \
  --path mnt/source/paperless/media/documents \
  --destination /tmp/restore-test/
```

### 3. Восстановить базу данных

Та проверка, которая действительно важна:

```bash
# В одноразовый контейнер — никогда не в рабочую БД
docker run -d --name pg-restore-test -e POSTGRES_PASSWORD=test postgres:17
zcat /opt/data/db-dumps/paperless-db.sql.gz | \
  docker exec -i pg-restore-test psql -U postgres
docker exec pg-restore-test psql -U postgres -c '\l'   # базы существуют? количество строк вменяемое?
docker rm -f pg-restore-test
```

### 4. Отрепетируйте катастрофу на бумаге

Спросите себя: *сервера больше нет; какова последовательность действий?* Вы должны уметь записать её по памяти:

1. Установить Devuan → [руководство по серверу](../linux/devuan-server-install.md)
2. Установить Docker → [руководство по homelab](docker-home-lab.md)
3. Клонировать homelab-репозиторий из Forgejo → `/opt/stacks` восстановлен
4. Восстановить `/opt/data` с NAS (Kopia) — или из внешнего репозитория (Borg), если NAS тоже погиб
5. Восстановить дампы баз данных в свежие контейнеры БД
6. `docker compose up -d`, стек за стеком

Если на каком-то шаге вы говорите «это мне пришлось бы выяснять» — выясните **сейчас** и запишите.

## 📟 Мониторинг (тихий отказ — поведение по умолчанию)

Бэкапы отказывают молча — заполнившийся диск, истёкший ключ, несмонтированный NAS — а узнаёте вы об этом в момент восстановления. Подключите их к существующему мониторингу:

- Добавьте push-монитор в **Uptime Kuma** и пингуйте его в конце каждого прогона бэкапа; тревога — если пинг не пришёл по расписанию
- borgmatic поддерживает это из коробки — добавьте в `config.yaml`:

```yaml
uptime_kuma:
  push_url: https://uptime-kuma.local/api/push/<token>
```

- Проверяйте `docker logs kopia` и `docker logs borgmatic` после любого изменения инфраструктуры

> Мониторьте **отсутствие успеха**, а не только наличие ошибок.

## 🚫 Чего не делать

- Не бэкапьте файлы живых баз данных; сначала дамп
- Не давайте контейнерам резервного копирования доступ на запись к исходным данным
- Не храните ключи шифрования только на машине, которую бэкапите
- Не позволяйте избыточности RAID или NAS маскироваться под бэкап — она защищает от отказа диска, но не от удаления, повреждения или вымогателей
- Не «настроил и забыл» — именно так на третий год обнаруживают, что бэкапы остановились на первом
